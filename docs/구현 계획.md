# 구현 계획

PRD(`docs/PRD.md`)를 어떻게 만들었는지 적는다.

## 1. 전체 모양

```
브라우저 ──> Streamlit (streamlit_app.py)  ──> actions.py ──> db.py ──> Supabase(PostgreSQL)
                                            │
                                            ├──> rules.py    (규칙 판단, 순수 함수)
                                            ├──> solver.py   (앱이 스스로 하는 배정)
                                            └──> ai_client.py ──> 오픈라우터 (모델 3개)
```

## 2. 파일

| 파일 | 하는 일 |
| --- | --- |
| `streamlit_app.py` | 화면. 공고 2.7절의 `key` 를 그대로 지정한다 |
| `actions.py` | DB를 바꾸는 일. 읽고 판단해서 쓰는 일을 한 거래 안에서 한다 |
| `rules.py` | 규칙 판단. DB도 Streamlit도 들어오지 않는 순수 함수만 둔다 |
| `solver.py` | 규칙을 지키는 배정을 모든 경우를 따져 찾는다 |
| `ai_client.py` | 오픈라우터 호출, 120초 제한, 1→2→3차 전환, 응답에서 JSON 꺼내기 |
| `roster.py` | 명단 CSV 읽기 (utf-8-sig) |
| `db.py` | 연결 묶음, 거래, `schema.sql` 실행 |
| `config.py` | 비밀 값 읽기. 값은 절대 돌려주거나 출력하지 않는다 |
| `keepalive.py` | DB 일시정지 막기. 깃허브 Actions 가 매일 돌린다 |
| `schema.sql` | 테이블을 만드는 SQL. 앱이 시작할 때 그대로 실행된다 |
| `tests/` | 연습용 시나리오와 잔 기능 시험 |

**규칙 판단을 `rules.py` 한 곳에만 둔 이유**: 앱(`actions.py`)과 시험(`tests/sim.py`)이
같은 함수를 부르게 하려는 것이다. 그래야 시험에서 통과한 규칙과 실제로 앱이 쓰는 규칙이
어긋날 수 없다.

## 3. 데이터

`schema.sql` 참고. 공고 5장의 최소 참고안에 두 가지를 더했다.

- `tf_applications` 에 부분 유일 인덱스 `tf_applications_one_pending` 을 두어, 한 학생이
  결과를 기다리는 지원을 둘 이상 가질 수 없게 DB에서도 막았다.
- `tf_ai_logs` 테이블을 더해 AI 호출을 모두 기록한다. README 7.1절 5항의 실패 사례를
  꾸며 내지 않고 실제 기록으로 쓰기 위함이다.

유일성 제약이 지켜 주는 것:

| 제약 | 지켜 주는 것 |
| --- | --- |
| `tf_members` 기본 키 `(team_id, slot_no)` | 마지막 자리에 두 명이 동시에 들어가면 먼저 도착한 학생만 기록 |
| `tf_members.student_id` unique | 한 학생은 한 팀에만 소속 |
| `check (slot_no between 1 and 4)` | 다섯 번째 자리를 막음 (정원 4명) |
| `tf_votes` 기본 키 `(application_id, voter_id)` | 한 번 투표하면 바꿀 수 없음 |
| `main_role`, `role` 의 `check (... in (...))` | 6개 역할 밖의 값을 막음 |

## 4. 핵심 규칙을 어떻게 계산하는가

### 4.1 필수 포함 역할 자리 (공고 3장의 어려운 해결)

"맡을 수 있는 사람이 있는가"를 세지 않고, **서로 다른 사람에게 하나씩 짝지을 수 있는
최대 개수**를 센다(`rules.required_filled`). 기획자와 웹 프로그래머는 서로 다른 학생이
맡아야 하므로, 둘 다 할 수 있는 학생 혼자만 있는 팀은 2개 가운데 1개만 채운 것이다.

지원을 막는 조건은 이렇다.

```
지원자가 들어간 뒤 남는 자리 수  <  그 팀에서 아직 채우지 못한 필수 포함 역할 수
```

### 4.2 승인 직전 재검사 (공고 3장의 어려운 해결)

지원할 때 한 번, **승인하려는 순간 다시 한 번** 검사한다. 같은 팀에 대기 중인 지원이
여럿이면 앞의 지원이 먼저 승인되어 팀이 바뀌기 때문이다. 처리 순서는 지원한 순서가 아니라
**투표가 끝난 순서**가 되는데, 이는 "모든 팀원이 찬성한 순간"에 승인 처리를 하므로
저절로 그렇게 된다.

### 4.3 동시에 들어오는 요청

지원과 투표는 하나의 거래 안에서 처리하고, 그 팀의 줄을 `SELECT ... FOR UPDATE` 로 잠가
같은 팀에 동시에 오는 요청을 한 줄로 세운다. 그래도 넘어가는 경우는 DB의 유일성 제약이
마지막으로 막는다.

### 4.4 앱이 스스로 하는 배정 (공고 3장의 어려운 해결)

되추적(backtracking)으로 모든 경우를 따진다. 가지치기는 네 가지를 쓴다.

1. 팀 인원 4명 초과 금지, 주 역할 중복 금지
2. 2명을 채우지 못하는 팀이 생기면 그만둔다
3. 팀마다 남은 자리가 빈 필수 역할 수보다 적으면 그만둔다
4. 필수 역할을 맡을 수 있는 남은 학생 수가 모자라면 그만둔다 (홀의 조건)

넣을 수 있는 팀이 가장 적은 학생부터 정한다(MRV). 배정 대상은 8명을 넘지 않으므로
연습용 시나리오에서는 3~38개 경우만 따지고 1밀리초 안에 끝난다.

### 4.5 배정이 아예 불가능할 때 (공고 2.5절 8항)

AI를 부르기 **전에** 위 되추적을 먼저 돌린다. 답이 없으면 AI를 부르지 않고
"규칙을 지키는 배정이 없음"과 이유를 보여 준다. 답이 있으면 그것을 손에 쥔 채로
AI에게 물어보고, AI가 3차까지 실패하면 쥐고 있던 답을 쓴다.

## 5. AI 호출

- 모델 3개를 1·2·3차로 정해 쓴다. 이름은 `config.py` 에 있고 Secrets 로 바꿀 수 있다.
- **120초의 전체 대기 시간**: `requests` 의 timeout 은 응답이 시작될 때까지만 재는 경우가
  많다. 그래서 호출을 다른 스레드에 맡기고 `future.result(timeout=120)` 으로 이쪽에서
  시계를 재, 120초가 지나면 기다리기를 그만두고 다음 모델로 넘어간다.
- 빈 응답, HTTP 오류(429 등), JSON 형식 오류, 검사 불통과를 모두 실패로 보고 다음 모델로 간다.
- 추론 모델이 생각하는 데 길이 한도를 다 써서 빈 응답을 내는 일을 줄이려고
  `reasoning.effort=low`, `max_tokens=4000` 을 준다.
- 전체에도 400초 한도를 두어 10분을 넘지 않게 한다 (공고 6.3절 18번).

## 6. 화면

- 공고 2.7절 표의 `key` 를 그대로 쓴다. `key` 에는 영문, 숫자, 밑줄만 쓴다.
- **로그인 단추는 `st.button` 으로 만든다.** 공고 표에는 `st.form_submit_button` 도 적혀
  있으나 그 함수에는 `key` 매개변수가 없어 `login_submit` 을 붙일 수 없다.
  폼을 쓰지 못하는 대신, 비밀번호 칸의 `on_change` 로도 로그인되게 해 두어
  글자를 넣자마자 단추를 눌렀을 때 클릭이 묻히는 일을 막았다.
- 결과 안내(`result`)는 `st.session_state` 에 담아 두고 화면을 다시 그릴 때마다 보여 준다.
  자동 갱신으로 화면이 다시 그려져도 안내가 사라지지 않게 하려는 것이다.
- 지원·투표 단추를 누르면 `st.rerun()` 으로 화면 전체를 다시 그린다. 조각(fragment)만
  다시 그리면 위쪽의 `result` 가 바뀌지 않기 때문이다.
- AI 배정 진행 안내는 단추보다 **먼저** 자리(`st.empty()`)를 만들어 둔다. 그래야 기다리는
  동안 그 자리에 "몇 차 모델을 기다리는 중"을 계속 적을 수 있다.

## 8. 배포

1. Supabase 프로젝트(6장 실습에서 쓴 것)의 연결 주소를 받는다.
2. 깃허브 비공개 저장소에 올린다. `.env` 는 `.gitignore` 로 걸러진다.
3. Streamlit Community Cloud 에서 비공개 저장소 읽기를 허락하고 배포한다.
   Main file path 는 `streamlit_app.py`.
4. Secrets 에 `OPENROUTER_API_KEY`, `DATABASE_URL`, `ADMIN_PASSWORD` 를 넣는다.
5. 앱 Settings > Sharing 에서 공개로 바꾸고, 시크릿 창으로 열어 로그인 화면이 보이는지 본다.
6. 저장소 Secrets 에 `DATABASE_URL` 을 넣어 매일 도는 DB 질의를 켠다.
